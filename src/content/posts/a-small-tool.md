这是一篇可替换的技术示例，使用“整理阅读链接”这一假设场景说明小工具的设计过程。文中的需求与代码用于演示，并不代表作者已经发布过对应产品。

## 先描述那个反复发生的麻烦

一个小工具的起点，往往不是某项新技术，而是一个重复出现的动作。比如阅读文章时把链接复制到笔记里，过几天又发现同一个页面被保存了三次。标题不一致，地址带着不同的参数，想重新找到它时还要逐个打开。

这时可以先用一句话描述需求：把输入的一组链接整理成不重复的列表，保持原有顺序，并指出无法识别的条目。这个描述已经足够具体，能帮助我们决定哪些事情现在不需要做。登录、分享、跨设备同步和推荐算法都可以暂时放下。

> 一个边界清楚的小工具，应该能让人解释它接收什么、返回什么，以及遇到问题时会发生什么。

### 把“好用”变成可观察的行为

“界面简洁”很难直接验证，“粘贴后只需要按一次按钮”就具体得多。同样，“结果可靠”可以拆成几种情况：空行被忽略，相同地址只保留一次，错误输入不会让其他内容全部消失。

| 输入情况 | 预期行为 | 需要避免的问题 |
| --- | --- | --- |
| 有多余空格 | 去除首尾空格 | 改动地址中间的合法字符 |
| 出现空行 | 安静地跳过 | 把空行当成错误 |
| 地址重复 | 保留第一次出现的位置 | 随机改变顺序 |
| 不是网址 | 单独列出供检查 | 静默丢失用户输入 |
| 包含查询参数 | 原样保留参数 | 错把不同资源合并 |

## 先让核心逻辑独立工作

下面的 JavaScript 函数只处理输入和结果，不操作页面。它要求地址包含 `http://` 或 `https://`，同时保留查询参数和片段。这是一项保守的选择：参数有时决定页面内容，贸然删除可能让整理后的链接指向不同资源。

```javascript
function organizeLinks(input) {
  const seen = new Set();
  const links = [];
  const invalid = [];

  for (const line of input.split(/\r?\n/)) {
    const value = line.trim();
    if (!value) continue;

    try {
      const parsed = new URL(value);
      if (!['http:', 'https:'].includes(parsed.protocol)) {
        invalid.push(value);
        continue;
      }

      const normalized = parsed.href;
      if (!seen.has(normalized)) {
        seen.add(normalized);
        links.push(normalized);
      }
    } catch {
      invalid.push(value);
    }
  }

  return { links, invalid };
}
```

这段实现没有尝试访问任何地址，因此不能判断网页是否存在。它所做的是解析与去重。在界面上也应该使用“无法识别的地址”这样的描述，避免把格式检查包装成可访问性检测。

如果需要了解地址解析的规则，可以查阅 [MDN 的 URL 说明](https://developer.mozilla.org/zh-CN/docs/Web/API/URL)。标准能力能够完成的工作，通常值得先交给标准能力。

## 再让界面解释结果

界面可以只有一个输入框、一个整理按钮和两块结果区域。成功的条目允许复制；无法识别的条目则保留原文，供用户修正。复制后需要给出明确反馈，复制失败也应该允许直接选中文字。

输入框应当有可见标签。按钮的名字可以直接叫“整理链接”，比“开始处理”更容易理解。没有输入时，告诉用户“一行粘贴一个完整网址”就足够了，不需要先显示一整页教程。

### 用几组真实输入试一试

检查时可以混合正常地址、空行、重复内容和错误文本。还应尝试只有一条记录、没有记录以及较长的地址。对小工具而言，这些输入往往比演示时最漂亮的一组数据更有价值。

如果后来发现用户经常保存不带协议的域名，可以明确增加相应规则，并在界面上解释会自动补全 `https://`。重要的是让规则逐步生长，而不是在第一版里猜测所有可能性。

## 留下下一次能看懂的说明

工具写完之后，用几行文字记录它解决的问题、运行方式和已知限制。未来回头修改时，这些说明比记忆可靠。也可以保留几组有代表性的输入，方便确认改动没有破坏原来的行为。

最后再问一次：这个工具是否减少了最开始那个重复动作？如果答案是肯定的，它就已经完成了一件实在的小事。更大的功能可以等待下一次真实的需要。
